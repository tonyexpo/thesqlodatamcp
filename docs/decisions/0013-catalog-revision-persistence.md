# ADR 0013 — SQLite/EF Core control store and durable `CatalogRevisions` storage

- **Status:** Accepted
- **Date:** 2026-09-06

## Context

ADR 0012 accepted `CatalogRevision` as an in-memory-only snapshot of one catalog build attempt, deliberately deferring "persistence" as later, separate Milestone 1 work. The backlog's next dependency-ordered item is "Add SQLite control-store migrations and catalog revision persistence." The authoritative handoff (`docs/AI_DATA_GATEWAY_HANDOFF.md`) and this repository's own `docs/architecture.md` ("Persistence" section) already mandate the technology: "v1 uses SQLite and EF Core migrations. EF is only for the internal schema," used "only for OpenIddict state, catalog revisions, hashed approval tokens, minimal admin audit, and required cryptographic state" — never against the reporting source. This slice is therefore not a build-vs-buy decision; it records the first concrete use of that already-settled technology and the entity shape needed to durably store a `CatalogRevision`.

`TheSqlODataMcp.Persistence` existed only as a boundary-marker class with no packages. No EF Core, SQLite, or Dapper reference existed anywhere in the solution before this slice.

## Decision

- Add `Microsoft.EntityFrameworkCore.Sqlite` and `Microsoft.EntityFrameworkCore.Design` 10.0.11 to `Directory.Packages.props` (central package management) and reference both from `TheSqlODataMcp.Persistence.csproj` (`Design` as a build-time-only tool dependency, `PrivateAssets="all"`, matching the existing `xunit.runner.visualstudio` pattern).
- Add a local `dotnet-ef` tool manifest (`.config/dotnet-tools.json`) so migrations remain reproducible for any future contributor without a global tool install. CI does not need it: `Database.Migrate()` at runtime uses only the EF Core runtime packages, never the `dotnet-ef` CLI.
- Add `StoredCatalogRevision` (`TheSqlODataMcp.Persistence.CatalogStore`), the durable row for one build attempt: a database-generated `Id`, `CreatedAt`, `Status` (EF Core's `CatalogRevisionStatus` reused directly rather than a duplicate Persistence-local enum, stored as a string column), `TechnicalHash` and `TechnicalCatalogJson` (always present — technical discovery happens before merging, mirroring `CatalogRevision`'s own always/nullable discipline), and `MergedHash`/`MergedCatalogJson` (present iff succeeded) or `ValidationResultJson` (present iff failed). Column and table naming (`CatalogRevisions`, `ValidationResultJson`) follows the handoff's own stated schema rather than inventing new names.
- **`StoredCatalogRevision` intentionally adds no "active" flag, no supersession reference, and no revision ordering beyond its own `Id`.** Tracking which revision currently serves, atomic activation, and last-valid rollback are the next, separate Milestone 1 slice (activation), not part of this one — mirroring ADR 0012's own scope discipline of not pulling forward work its type doesn't need yet.
- Add `CatalogRevisionMapper.ToStored(TechnicalCatalog, CatalogRevision)`. **`CatalogRevision` alone cannot produce a full `TechnicalCatalogJson` when the merge failed** — a failed revision retains only `TechnicalHash`, not the source `TechnicalCatalog` object, so the mapper takes the technical catalog as a separate parameter (exactly the object a caller already holds immediately before calling `CatalogRevisionFactory.Create`) and asserts its hash matches the revision's `TechnicalHash` before trusting it. On the success path it symmetrically re-verifies `revision.MergedHash` against a freshly computed hash of `revision.MergedCatalog` before persisting either — `CatalogRevision.Success` is a public factory that trusts its caller's `mergedHash` argument, so without this check a hand-built, internally-inconsistent `CatalogRevision` could otherwise flow into permanent storage uncaught (the real production path, `CatalogRevisionFactory.Create`, always computes both hashes itself and is never inconsistent, but the mapper does not assume it is the only caller).
- Add `CatalogRevisionStore` (`SaveAsync`, `GetAsync`) over a new `ControlStoreDbContext`, and an initial `InitialCreate` EF Core migration creating the `CatalogRevisions` table.
- **Deliberately out of scope for this slice:** reconstructing a live `MergedCatalog`/`TechnicalCatalog` object graph from a stored row. `MergedCatalogCanonicalJson`'s output is a deliberately partial "diff" view for hashing (entity `schema`/`name`, field `name`/`ordinal` — not full provider type/nullability/identity detail, which lives only on `TechnicalEntity`/`TechnicalField`); a full round-trip therefore needs both stored JSON blobs plus a currently-nonexistent JSON→domain-object deserializer. Nothing consumes a reconstructed live catalog yet — the next slice (activation) is the first real consumer, so building that deserializer now would be speculative. `GetAsync` returns the raw stored row; tests prove exact byte-for-byte round-trip of the JSON text and hashes, not object-graph reconstruction.
- New test project `tests/TheSqlODataMcp.Persistence.Tests`, with `SqliteControlStoreFixture` mirroring `SqlServerReportingCatalogFixture`'s private-constructor-plus-static-factory-plus-`IAsyncDisposable` shape, but using a real temp-file SQLite database (no Docker/Testcontainers needed) whose deletion is verified after disposal. Tests carry no `[Trait("Category", ...)]` and run inside the existing `validate` CI job.

## Defect found and fixed during review

The first draft made all seven `StoredCatalogRevision` properties get-only (`{ get; }`), matching this repository's usual immutable-domain-type style, with a private parameterless constructor added only to satisfy EF Core's constructor-binding materialization path. `dotnet ef migrations add` did not fail — it silently produced a migration with only 5 of 8 required columns, dropping `MergedHash`, `MergedCatalogJson`, and `ValidationResultJson` entirely from the model with no error or warning. This was caught by rebuilding and inspecting the generated migration's column list rather than trusting a successful `dotnet ef migrations add` exit code alone.

The cause, confirmed by an independent reviewer building an isolated repro (an initial draft of this ADR misattributed it to value-vs-reference-type property defaults, which a targeted repro disproved): **a get-only property is dropped from the model unless `OnModelCreating` explicitly configures it via `.Property(x => x.Foo)`.** `ControlStoreDbContext`'s draft only called `.Property(...)` for `Status`, `CreatedAt`, `TechnicalHash`, and `TechnicalCatalogJson` — exactly the four that survived — never for `MergedHash`, `MergedCatalogJson`, or `ValidationResultJson`, which were left to pure convention and silently excluded. Whether a property is a value or reference type is irrelevant to this rule; a future nullable value-typed column (e.g. `int?`) added the same way, without both a setter and an explicit `.Property()` call, would reproduce the exact same silent drop. Fixed by giving every property a `private set` (the standard, unambiguous EF Core entity-property pattern) so materialization always uses ordinary property setters instead of depending on `OnModelCreating` naming every property; the regenerated migration correctly includes all eight columns regardless of which properties `OnModelCreating` explicitly configures.

The same independent review also flagged two smaller gaps, both fixed before commit: `CatalogRevisionMapper.ToStored` verified the technical hash but not the merged hash before trusting a `CatalogRevision` (see the `MergedHash` re-verification described above), and `.gitignore` had no rule protecting against `ControlStoreDbContextFactory`'s design-time SQLite file ever being accidentally committed (added `*.db`/`*.db-shm`/`*.db-wal`). It additionally identified a real coverage gap — no test exercised non-ASCII overlay text through an actual SQLite round-trip — closed by `SaveThenGetRoundTripsNonAsciiOverlayTextByteForByteThroughSqlite`.

## Consequences

- `CatalogRevisionStore` gives the next slice (atomic activation, last-valid rollback, bootstrap modes) a tested, already-durable place to persist and read back every build attempt, without that slice needing to design its own schema or JSON round-trip discipline.
- No "active revision" concept, no object-graph deserializer, and no bootstrap-mode logic exist yet; a `MergedCatalog` still cannot be reconstructed from storage. This is deliberate, recorded scope — not an oversight.
- `.config/dotnet-tools.json` is now a repository convention for any future EF Core migration (e.g. Milestone 5's OpenIddict state).
