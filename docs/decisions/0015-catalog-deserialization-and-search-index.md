# ADR 0015 — Catalog JSON→domain deserialization and in-memory search index

- **Status:** Proposed
- **Date:** 2026-09-06

## Context

ADR 0014 covered atomic activation, last-valid rollback, and bootstrap modes, and named exactly what it deliberately left out. The backlog's Milestone 1 item is one bullet — "Implement atomic activation, last-valid rollback behavior, bootstrap modes, and in-memory catalog/search indexes" — and ADR 0014 only closed its first half. Its own Consequences said what the remaining half needs: "Milestone 3's actual host startup sequence... still needs... a JSON→domain deserializer for the case where no rebuild happens but the process still needs a live `MergedCatalog` in memory." The handoff's lifecycle (`docs/AI_DATA_GATEWAY_HANDOFF.md`, "Control store") lists this explicitly as step 3, "Load last active revision," followed by step 9, "Build in-memory catalog/search" — and its `search_catalog` tool spec reads: "Search names, fields, aliases, descriptions, warnings, and relationships. Return compact ranked matches."

## Decision

- Add `TechnicalCatalogCanonicalJson.Deserialize` — the exact inverse of `Serialize`. Every domain object is rebuilt through its own existing public constructor, so the same invariants `Serialize`'s input already satisfied are re-checked on the way back in. Implemented with `System.Text.Json` record deserialization (`PropertyNameCaseInsensitive`) against private DTOs shaped to match the writer's camelCase properties, the same idiom `CatalogRevisionMapper.DeserializeErrors` already used for validation errors.
- Add `MergedCatalogCanonicalJson.Deserialize(json, technicalCatalog)` — the inverse of `Serialize`, but it cannot stand alone: `Serialize`'s canonical JSON deliberately omits everything that never affects the overlay-attributable structural hash (a field's canonical/provider type, keys, indexes — see its own class remarks), so each `MergedEntity.Physical`/`MergedField.Physical` is taken from the supplied, already-deserialized `TechnicalCatalog` instead, matched by identity/name exactly the way `CatalogMerger` itself does it.
- Add `CatalogRevisionMapper.ToDomain(StoredCatalogRevision)` (Persistence) — the exact inverse of the existing `ToStored`. For a succeeded row it chains both deserializers together and re-anchors the merged catalog to the freshly rebuilt technical catalog; for a failed row it only needs `DeserializeErrors`, matching how little `CatalogRevision.Failure` itself retains.
- Add `CatalogSearchIndex` (`TheSqlODataMcp.Core.Catalog`), built from one `MergedCatalog`: `FindEntity(PhysicalObjectIdentity)` is an O(1) dictionary lookup; `Search(query, maxResults)` is a ranked scan across entity/field names, display names, aliases, descriptions, catalog-level warnings, and relationships — exactly the surface `search_catalog` names. A name-like match (a name, display name, alias, or relationship name) always outranks a free-text match (a description or warning) at the same exactness (exact / prefix / substring); ties break deterministically by entity schema/name, then match kind, then matched text.
- **Deliberately simple, not precomputed:** `Search` scans the catalog on every call instead of building an inverted term index at construction. Nothing consumes this yet, and a single reporting catalog's entity count is small under this project's already-documented single-instance v1 constraint (`docs/architecture.md`), so a real index structure would be sized against a usage pattern that doesn't exist yet. Revisit if a real caller makes this measurably hot.
- **Deliberately out of scope:** the `search_catalog`/`describe_entities` MCP tool façades themselves — JSON schemas, pagination, and any ranking tuned against real usage are Milestone 4 work built on top of `CatalogSearchIndex`, not part of it. Also out of scope: wiring any of this into `CatalogBootstrapCoordinator` or an actual host startup sequence. That composition — `CatalogRevisionMapper.ToDomain(await coordinator.RunAsync(...))` then `new CatalogSearchIndex(revision.MergedCatalog!)` — is exactly what Milestone 3's host lifecycle will do, and this slice's own tests exercise it end-to-end without needing the host to exist.

## Independent review

Reviewed by a freshly spawned, independent agent with no visibility into this implementation's own reasoning, per this repository's standing practice of never accepting a slice on the implementer's self-report alone. The reviewer built and ran the full suite itself, then went further: wrote and ran (then deleted) scratch adversarial tests exercising round-trip fidelity of every invariant-bearing field (a composite key, a filtered index, `IsRowVersion`, `IsPersistedComputed`, a relationship), fed both `Deserialize` methods deliberately malformed/adversarial JSON (truncated input, an unknown enum wire-name, a missing required nested object), fed `MergedCatalogCanonicalJson.Deserialize` a structurally different "imposter" `TechnicalCatalog` sharing the same entity/field identity, and hand-verified the search index's ranking and dedup logic against cases the shipped tests didn't cover. No blocking defect existed in the original implementation, but the review surfaced five real gaps, all closed before this ADR was accepted:

1. **Silent data substitution.** `MergedCatalogCanonicalJson.Deserialize` performed no cross-check between the merged JSON's own `catalogVersion`/`provider` and the supplied `TechnicalCatalog`'s, so a structurally different but identity-matching `TechnicalCatalog` was silently accepted, substituting wrong physical field data with no error — proven with a reproducible scratch test. Fixed by adding the same catalog-version/provider guard `CatalogMerger` already performs, which is also what makes the Decision section's "matches...exactly the way `CatalogMerger` itself does it" claim actually true rather than aspirational.
2. **Unhandled crash on missing nested JSON.** A persisted row missing its `providerType` object crashed `TechnicalCatalogCanonicalJson.Deserialize` with a raw `NullReferenceException` instead of a typed exception. Fixed with an explicit null check in `ToField`, now a clean `ArgumentException` naming the offending field.
3. **Inconsistent malformed-input handling.** Syntactically broken JSON threw a raw `System.Text.Json.JsonException` from both `Deserialize` methods, while whitespace/`"null"` input was already wrapped into `ArgumentException` — a caller catching `ArgumentException` uniformly to handle "bad catalog JSON" would miss the truncated-JSON case. Both methods now wrap `JsonException` the same way.
4. **No defense-in-depth hash verification on the way out.** `CatalogRevisionMapper.ToDomain` trusted a stored row's hash strings verbatim, asymmetric with `ToStored`'s explicit hash verification on the way in. `ToDomain` now recomputes and verifies both the technical and merged structural hash against the freshly rebuilt objects before returning, mirroring `ToStored` exactly.
5. **Dedup could silently drop a distinct match.** `CatalogSearchIndex`'s duplicate-match guard keyed only on `(Entity, Kind, Text)`, so two different fields on the same entity sharing identical display-name/alias/description text collapsed into a single match with no way to tell them apart — confirmed with a scratch test. Fixed by adding `Field`/`Relationship` to both the dedup key and to `CatalogSearchMatch` itself, so genuinely distinct matches are both returned and distinguishable; `CatalogSearchMatch`'s constructor now also rejects a field/relationship match with no owning entity.

Two of the reviewer's scratch-test scenarios (the missing-field case for `MergedCatalogCanonicalJson.Deserialize`, and the shared-display-name case for `CatalogSearchIndex`) were also added as permanent tests rather than only fixed in the implementation.

## Consequences

- The control store's persisted rows are no longer a dead end at process restart: `CatalogRevisionMapper.ToDomain` turns a stored row back into a live `CatalogRevision` (and, when succeeded, a live `MergedCatalog`) with no re-introspection needed, and verifies both structural hashes against the rebuilt objects before returning.
- `CatalogSearchIndex` gives Milestone 4's `search_catalog`/`describe_entities` tools a ready-made data structure to sit on, closing the backlog's "in-memory catalog/search indexes" item alongside ADR 0014's activation/rollback/bootstrap-mode half. Its `CatalogSearchMatch` result exposes the specific `Field`/`Relationship` that matched, not just the owning entity, so two distinct matches on the same entity are never conflated.
- `CatalogSearchIndex.Search`'s ranking is a simple, hand-written heuristic (exact/prefix/substring, name-like beats free-text), not tuned against any real query log — expect Milestone 4 to revisit it once real usage exists.
- Both `Deserialize` methods now reject a structurally mismatched input as early and cheaply as possible (a version/provider guard before any per-entity work), while `CatalogRevisionMapper.ToDomain` is the authoritative, expensive check (a full hash recomputation) for the one real call path. Direct callers of the `Deserialize` methods outside `ToDomain` still get the cheap guard but not the hash guarantee — that asymmetry is deliberate, not an oversight: only `ToDomain` has the stored hash to check against.
