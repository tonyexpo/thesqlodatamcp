# ADR 0014 — Atomic catalog activation, last-valid rollback, and bootstrap modes

- **Status:** Accepted
- **Date:** 2026-09-06

## Context

ADR 0013 built durable, append-only storage for `CatalogRevision` build attempts but deliberately tracked no "active" revision. The backlog's next Milestone 1 item is "Implement atomic activation, last-valid rollback behavior, bootstrap modes, and in-memory catalog/search indexes." This ADR covers activation, rollback, and bootstrap modes; the in-memory catalog/search index is separate follow-up work, since it is the first real consumer of a JSON→domain-object deserializer that nothing needs yet (mirroring ADR 0013's own "no object-graph reconstruction" scope decision).

The handoff (`docs/AI_DATA_GATEWAY_HANDOFF.md`, "Control store") gives an indicative `CatalogRevisions` schema of `Id`, `CreatedAt`, `ActivatedAt`, `Status`, ... — `ActivatedAt` lives on the revision row itself, not in a separate pointer table. The handoff's merge rules also state directly: "A failed refresh preserves the last valid revision," and its four bootstrap modes (`Disabled`, `ImportIfEmpty`, `ImportIfChanged`, `AlwaysImport`) already exist as a plain config string in `appsettings.json`'s `Catalog:BootstrapMode`, with no behavior behind it yet.

## Decision

- Add `ActivatedAt` (nullable `DateTimeOffset`) directly to `StoredCatalogRevision`, matching the handoff's own schema instead of inventing a separate active-pointer table. "Currently active" is defined as the row with the greatest non-null `ActivatedAt`; activating a new revision never requires clearing any other row, since an older row's past `ActivatedAt` values remain a harmless activation-history trail.
- `StoredCatalogRevision.Activate(DateTimeOffset)` is the only way to set `ActivatedAt`, and it throws `InvalidOperationException` for a failed revision. **This throw is the entire last-valid-rollback guarantee**: nothing "restores" the previous revision on failure — a caller that only ever activates a revision after observing `Succeeded` simply never reaches a state where the previously active row is touched.
- `CatalogRevisionStore` gains `GetActiveAsync` (client-side ordering by `ActivatedAt` then `Id`, since SQLite's EF Core provider cannot translate `ORDER BY` over `DateTimeOffset` into SQL — the ever-activated row count is expected to stay small for a single-instance v1 deployment) and `ActivateAsync(id, activatedAt)` (loads the tracked row, calls `Activate`, and saves — one row update through one `SaveChangesAsync` call, which is what makes activation atomic).
- Add `CatalogBootstrapMode` (`Disabled`, `ImportIfEmpty`, `ImportIfChanged`, `AlwaysImport`) and `CatalogBootstrapPolicy.ShouldImport(mode, hasActiveRevision, technicalCatalogChanged)` to `TheSqlODataMcp.Core.Catalog` — a pure, one-switch-expression decision table with no I/O, kept independent of persistence and introspection so it needs no fixture to test.
- Add `CatalogBootstrapCoordinator` (`TheSqlODataMcp.Persistence.CatalogStore`), the orchestration this backlog item is actually asking for: given the current active revision and a freshly discovered `TechnicalCatalog`, it asks the policy whether to rebuild, and if so runs `CatalogRevisionFactory.Create`, persists the result either way, and activates it only if it succeeded. It stays provider-agnostic — SQL Server introspection and semantic overlay loading remain the caller's responsibility, exactly like `CatalogRevisionFactory` already does.
- **Deliberately out of scope:** wiring `CatalogBootstrapCoordinator` into an actual ASP.NET Core host startup sequence, and binding `Catalog:BootstrapMode` config to `CatalogBootstrapMode` through `IOptions<T>`. `TheSqlODataMcp.Web`'s `Program.cs` does no real startup work yet — building the host, its lifecycle (open/migrate SQLite → load last active revision → introspect → merge → validate → atomically activate → build in-memory catalog/search → mark ready), and its readiness semantics is explicitly Milestone 3 scope ("Build the ASP.NET Core host, configuration validation...") per the backlog, not Milestone 1. Wiring this in now would be a dangling, unconsumed config binding.
- **Deliberately out of scope:** reconstructing a live `MergedCatalog`/`TechnicalCatalog` object graph from a stored row, and any in-memory search index built from it. Nothing in this slice's own tests needs a reconstructed live catalog — `CatalogBootstrapCoordinator`'s tests supply an already-in-memory `TechnicalCatalog` directly, the same way `CatalogRevisionFactoryTests` already does. This deserializer is the next slice's actual job, colocated with its first real consumer.

## Independent review

Reviewed by a freshly spawned, independent agent with no visibility into this implementation's own reasoning, per this repository's standing practice of never accepting a slice on the implementer's self-report alone. The reviewer re-ran every build/test/format command itself, reverted `GetActiveAsync` to a server-side `OrderByDescending` to confirm the SQLite `DateTimeOffset` limitation is real (it throws `NotSupportedException`, not just a plausible-sounding claim), inspected the raw SQLite file with a separate ADO.NET connection to confirm `ActivatedAt` round-trips correctly outside of EF Core's own query cache, forced an exact `ActivatedAt` tie between two rows to confirm the `Id`-descending tie-break picks the right one, and hand-derived the full `CatalogBootstrapPolicy` truth table against the test file. No incorrect claim and no blocking defect was found. Three low-severity gaps were identified and addressed:

1. `GetActiveAsync` materializes every ever-activated row's full JSON blobs, and since `ActivatedAt` is never cleared on supersession, that set grows unboundedly under `AlwaysImport` with no retention policy anywhere in this repository. Recorded below as a known limitation rather than fixed now — no consumer depends on `GetActiveAsync`'s performance yet, and a retention policy without a real usage pattern to size it against would be speculative.
2. `CatalogBootstrapCoordinator.RunAsync` covers `GetActiveAsync → decide → SaveAsync → ActivateAsync` with no transaction or lock; under concurrent invocation, which row ends up active depends on caller-supplied timestamps rather than commit order. Not reachable today (no host wiring exists yet), and consistent with this repository's already-documented single-instance v1 constraint (`docs/architecture.md`), but that assumption is now stated explicitly for this code path in Consequences below rather than left implicit.
3. No test activated the same revision twice. Closed by `CatalogRevisionStoreTests.ActivatingTheSameRevisionTwiceOverwritesItsActivatedAtTimestamp`.

## Consequences

- The control store can now answer "what is the active revision" and "activate this one," and a caller can implement any of the four bootstrap modes without re-deriving the decision logic.
- Milestone 3's actual host startup sequence has a tested `CatalogBootstrapCoordinator` to call into; it still needs to supply real SQL Server introspection, a loaded `SemanticOverlay`, and (per the handoff's lifecycle step 3, "load last active revision") a JSON→domain deserializer for the case where no rebuild happens but the process still needs a live `MergedCatalog` in memory.
- No in-memory catalog/search index exists yet; `GetActiveAsync` returns only the raw stored row. This is deliberate, recorded scope, not an oversight.
- `GetActiveAsync`'s ever-activated row set (and the JSON blobs it materializes per row) grows unboundedly over a deployment's lifetime under `AlwaysImport`, since `ActivatedAt` is never cleared on supersession and no pruning/retention policy exists yet. Revisit before `AlwaysImport` sees real production use.
- `CatalogBootstrapCoordinator.RunAsync` assumes a single caller at a time (consistent with `docs/architecture.md`'s already-documented single-instance v1 constraint): it covers `GetActiveAsync → decide → SaveAsync → ActivateAsync` with no transaction or lock, so concurrent invocations could activate the wrong revision relative to real commit order. Milestone 3 must not call this from more than one place (e.g. a startup path and a concurrent admin-triggered refresh) without adding that coordination.
