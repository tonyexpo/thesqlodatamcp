# Adversarial QA — 2026-10-28T19:13:22Z

- Reviewer: Claude Code, clean context, **read-only**. This report is the only file added; it lives on the branch `main-qa`, not on `main`.
- Baseline: `main` at `14a7f02` («docs: record CI acceptance for the SqlClient upgrade»). Milestone 0 and Milestone 1 are declared complete; Milestone 2 (CQM and query compiler) has not started, so **there is no runnable gateway yet**. The review is therefore of the catalog foundation (Core, SqlServer introspection, Persistence), the scaffold configuration, the CI workflow and the documents that make claims about them. It is also a review of **seams**: choices made now that the protocol adapters will inherit.
- **Not executed.** The environment has no .NET SDK, Docker or SQL Server, which the repository itself records as a limitation of agent sandboxes. Everything below comes from reading the code, the tests and the ADRs, and from `grep` over the whole tree. Where a claim rests on the behaviour of a library (YamlDotNet, SQL Server catalog views) and not on this repository, it is marked and should be confirmed by a test before it is fixed.
- Scope: `src/` (Core: catalog model, overlay importer, merger, revision, search index, canonical JSON; SqlServer: introspector, projection, type mapper; Persistence: store, bootstrap coordinator, mapper; Web: `Program.cs`, `appsettings.json`), `tests/` as a map of what is and is not covered, `.github/workflows/ci.yml`, `Directory.*.props`, `global.json`, `spikes/` (skimmed), ADR 0006–0015, `docs/architecture.md`, `docs/backlog.md`, `docs/roadmap.md`, `docs/development-state.md`, the project skill and the handoff sections on exposure, authentication and bootstrap.
- Method: this product is a *read-only data gateway whose security rests on what the catalog says is visible*. So the questions were: where does a table stop being exposed, who decides, and at which layer is that decision enforced? Then: what happens to the catalog pipeline when the input is hostile (an overlay file), unusual (a modern SQL Server feature) or simply changed (a restart).

## Summary

The code that exists is careful: types are validated, constructors enforce invariants, hashes are checked on both write and read, the introspection query takes no caller input, and the repository's own history shows real defects found and fixed by independent review. This report does not dispute that.

What it finds is that **the controls the product is *for* are not built yet, and the places where they will have to plug in are open by default**:

1. **`exposed: false` is not enforced anywhere** (TS-01). Every layer defaults to visible, the merge deliberately does not filter, and the one consumer that exists — the catalog search index that Milestone 4's `search_catalog` tool is meant to sit on — returns hidden entities with their names, descriptions and relationships. No backlog item and no test asserts the filter.
2. **`DataSource:IncludedSchemas` and `ExcludedObjects` are read by nothing** (TS-02). They appear in `appsettings.json` and the handoff, nowhere in code, tests or backlog. The introspector discovers every user schema of the database.
3. **In the default bootstrap mode an edited overlay is silently ignored** (TS-03). `ImportIfChanged` compares only the technical hash; an administrator who sets `exposed: false` on a table and restarts gets the old catalog and no message.
4. **A hostile or accidental overlay can exhaust memory or the stack** (TS-04): no size, depth or alias limit on the YAML, recursive conversion, only `YamlException` caught, and no test of any of it.
5. **One unusual column can make the whole catalog impossible to build** (TS-05): introspection is all-or-nothing and its errors do not name the object.

None of these is exploitable today, because nothing is exposed to a caller. They are cheaper to fix now than after three protocol adapters depend on them.

## Findings

### TS-01 — `exposed: false` is not enforced by any layer, and the search index returns hidden entities
- **Severity**: high (by design hazard, not yet reachable)
- **Area**: exposure / catalog
- **Where**: `Core/Catalog/CatalogMerger.cs:195` (`var exposed = overlayEntity?.Exposed ?? true;`), `Core/Catalog/MergedCatalog.cs:5-15` (the merge "never filters based on `Exposed`… that belongs to a later, different slice"), `Core/Catalog/CatalogSearchIndex.cs` (no reference to `Exposed` anywhere: `Search`, `FindEntity`), `docs/decisions/0015-catalog-deserialization-and-search-index.md:44`, `docs/backlog.md`, `tests/…/CatalogSearchIndexTests.cs`.
- **What**: three decisions, each reasonable alone, add up to a fail-open chain:
  1. the default is *exposed* (handoff §"Default: every discovered user table/view is visible to authenticated callers unless globally excluded", and `?? true`);
  2. the merged catalog deliberately keeps hidden entities and delegates the filter to "protocol adapters";
  3. the first consumer, `CatalogSearchIndex`, was written to be what `search_catalog` and `describe_entities` "sit on" (ADR 0015) and iterates `Catalog.Entities` as given. `Search` matches entity names, display names, descriptions, aliases, field names, field descriptions and relationship names/descriptions of **every** entity, hidden or not; `FindEntity(identity)` returns a hidden entity to anyone who can name it.
  
  `grep -rn Exposed src tests` shows the flag being written, canonicalised, hashed and asserted *as a value* (`Assert.False(invoiceEntity.Exposed)`), and never used to decide anything. The backlog has no item for the filter (the only "filter" entries are OData `$filter`), no test asserts that a hidden entity is absent from a search, and the exposure rule is not in any ADR's "consequences".
- **Why it matters**: `exposed:false` is the administrator's tool for saying "this table must not be visible to AI clients". The catalog text is not neutral metadata here: `MS_Description` extended properties and the overlay's narrative are free text that people write about sensitive tables. Whoever wires the MCP tool to the existing index leaks them with no line of code that looks wrong.
- **Suggested fix**: make the filter a type, not a convention — a single `ExposedCatalogView` (or `MergedCatalog.Exposed()` returning a catalog without hidden entities **and** without relationships that target them) that is the *only* thing `CatalogSearchIndex` and every adapter accepts; add the backlog item and an architecture-level rule; test that a hidden entity, its fields, its descriptions and a relationship pointing at it are all absent from `Search`, `FindEntity` and any future describe call. Decide explicitly whether the default should stay fail-open for entities that no overlay mentions (see TS-02).
- **Confidence**: high (the absence of any reference is a grep result).

### TS-02 — The schema allow-list in the configuration is not implemented, and the introspector discovers everything
- **Severity**: high (same class as TS-01)
- **Area**: exposure / configuration
- **Where**: `Web/appsettings.json` (`DataSource:IncludedSchemas: ["sales","dbo"]`, `ExcludedObjects: []`), `SqlServer/SqlServerCatalogIntrospector.cs` (constructor takes only a connection string and a timeout; the query hard-codes `[s].[name] NOT IN (N'sys', N'INFORMATION_SCHEMA')`), `Core/Catalog/CatalogMerger.cs`, `tests/…/ScaffoldConfigurationTests.cs`.
- **What**: `grep -rn "IncludedSchemas\|ExcludedObjects" src tests docs` finds the two keys in `appsettings.json` and the handoff and **nowhere else**: not in code, not in a test, not in the backlog. The configuration reads as if it limited what the gateway sees; today it limits nothing. The introspector returns every user table and view of every schema the login can see, the technical catalog (with all `MS_Description` text) is serialised to the SQLite control store, and the merge exposes all of it by default (TS-01). The shipped defaults list `dbo`, the schema where "everything else" usually lives.
- **Forward-compatibility trap**: when the allow-list is added, `SqlServerCatalogProjection.CreateCatalog` will throw `"SQL Server foreign-key target is not part of the technical catalog."` for any foreign key from an included table to an excluded one, because it requires every FK target to be in the catalog. The first real database with a cross-schema FK will fail to bootstrap unless the projection learns to drop such relationships.
- **Why it matters**: the default exposure rule ("visible unless globally excluded") is only as safe as the exclusion mechanism, and that mechanism is a configuration key with no implementation and no owner in the plan.
- **Suggested fix**: give the introspector an options object (`IncludedSchemas`, `ExcludedObjects`) applied **in the SQL** (so excluded objects never enter memory, the control store or a log), define how foreign keys to excluded objects are handled, validate the keys at startup, add the backlog item, and test it against the reporting-catalog fixture with a second schema.
- **Confidence**: high.

### TS-03 — In the default bootstrap mode, an overlay-only change is silently not imported
- **Severity**: high (a security-relevant edit is dropped without a message)
- **Area**: bootstrap / lifecycle
- **Where**: `Persistence/CatalogStore/CatalogBootstrapCoordinator.cs` (`changed = active is null || !string.Equals(active.TechnicalHash, freshHash, …)`), `Core/Catalog/CatalogBootstrapMode.cs` (`ImportIfChanged => !hasActiveRevision || technicalCatalogChanged`), `Web/appsettings.json` (`Catalog:BootstrapMode: "ImportIfChanged"`), `docs/decisions/0014-…md`, `tests/…/CatalogBootstrapCoordinatorTests.cs`.
- **What**: the coordinator decides "changed" from the **technical** catalog hash alone. The overlay is not compared with anything. An administrator who edits the overlay — sets `exposed: false` on a table, fixes a description, adds a warning — and restarts finds that nothing is imported as long as the database schema is the same: the active revision, built from the old overlay, keeps serving. The mode is called `ImportIfChanged`, is the default, and the ADR describes the parameter as `technicalCatalogChanged` without saying that overlay changes do not count. The stored merged hash exists (`MergedHash`) and is the right thing to compare against, but the coordinator never computes the merged hash of the *candidate* before deciding. All six coordinator tests pass `overlay: null`; none exercises a changed overlay.
- **Why it matters**: the failure is silent (no log, no failed revision, the call returns the previous active revision as if all were well) and the thing being ignored is the instrument for hiding data (TS-01).
- **Suggested fix**: decide "changed" from `(technicalHash, overlayHash)` — or build the candidate revision, compare its `MergedHash` with the active one, and persist only on difference; log which input changed; rename the policy parameter; add the test pair "same schema, overlay changed → imported" and "same schema, same overlay → skipped".
- **Confidence**: high (the code and the test list are unambiguous).

### TS-04 — Overlay import has no limits: YAML aliases, nesting and input size
- **Severity**: medium (availability; the input is administrator-authored today, an upload or a shared repository tomorrow)
- **Area**: parsing / availability
- **Where**: `Core/Catalog/SemanticOverlayImporter.cs` (`ParseYamlToJson` → `YamlStream.Load`, `ConvertYamlNode`, `ConvertSequence`, `ConvertMapping`; `catch (YamlException)` is the only handler), `SemanticOverlayYamlDto`, tests.
- **What**:
  - **Aliases.** `YamlStream` resolves YAML anchors and aliases to shared nodes; `ConvertYamlNode` then walks them as a tree. A document of a few hundred bytes in which each anchored sequence refers to the previous one several times ("billion laughs") expands exponentially in time and memory during the conversion to `JsonNode`, before the schema or the strict deserializer run. Nothing limits input length, node count, alias count or expansion.
  - **Depth.** The conversion is recursive with no depth guard; deeply nested sequences or mappings can exhaust the stack, which in .NET is a process crash, not an exception.
  - **Exceptions.** Only `YamlException` is caught. `NotSupportedException` from the conversion and, as far as I know the library, an `ArgumentException` for duplicate mapping keys during `YamlStream.Load` (to be confirmed with a one-line test) would escape the import, which is documented to return a `SemanticOverlayImportResult.Failure` collecting every problem.
  - **Markdown.** `Markdown.Parse` of the whole body is also unbounded, but linear.
  - **Tests.** `SemanticOverlayImporterTests`/`QaTests` cover missing front matter, unknown keys, concurrency and constructor invariants; none covers an alias, a duplicate key, deep nesting or a large file.
- **Suggested fix**: reject input above a configured size before parsing; walk the `YamlStream` with a depth counter and a node budget and refuse alias-expanded documents (or disable aliases by pre-scanning for `&`/`*` events with the parser); catch `Exception` from the parse/convert stage and report it as `YamlSyntaxInvalid`; add the four tests.
- **Confidence**: medium–high on the mechanism (the recursion and the single catch are in the code); medium on the exact exception for duplicate keys.

### TS-05 — Introspection is all-or-nothing, and its errors do not say which object failed
- **Severity**: medium
- **Area**: introspection / robustness
- **Where**: `SqlServer/SqlServerCatalogProjection.cs` (`ValidateRow`: `GeneratedAlwaysType is < 0 or > 2` throws; `CreateEntity`; the foreign-key target check), `SqlServer/SqlServerTypeMapper.cs` (`ValidateExactMetadata`, `Decimal`, `Temporal`, `Character`… throw `ArgumentOutOfRangeException` with generic messages), `SqlServer/SqlServerCatalogIntrospector.cs`.
- **What**: every deviation from the expected shape aborts the whole catalog build:
  - `generated_always_type` is accepted only for 0, 1, 2. Per the SQL Server documentation the column also takes 5–8 for **ledger** tables (transaction-id and sequence-number columns), so a database that contains one ledger table (SQL Server 2022 and Azure SQL) makes `IntrospectAsync` throw `"SQL Server generated-always metadata is not supported by this catalog slice."` and the gateway has no catalog (to be confirmed against a ledger table on the fixture).
  - The type mapper validates `max_length`/`precision`/`scale` against the exact bands for known types and throws on any mismatch, which is the right stance for a *type* but means one exotic column (or a new SQL Server version that changes a band) blocks every other object.
  - The messages — `"Decimal storage length does not match its precision."`, `"SQL Server metadata rows for one object are inconsistent."`, `"…foreign-key target metadata is inconsistent."` — carry no schema, table or column name, so the operator cannot find the object that failed.
  - The documented conservative behaviour ("unsupported, spatial, hierarchical, variant and user-defined names remain `unknown`") applies to *type names*, not to these structural checks.
- **Why it matters**: an all-or-nothing catalog makes availability depend on the least typical object in the database; with the exposure model of TS-01/02 the operator's natural reaction (exclude the object) is not available (TS-02).
- **Suggested fix**: wrap each object (and each column) so a failure produces a *named* diagnostic and the object is skipped with a warning in the revision, or the revision fails with the list of all offending objects at once; accept the ledger values (or skip ledger system columns explicitly); include `schema.object.column` in every message.
- **Confidence**: high on the structure; medium on the ledger values (documentation, not a fixture run).

### TS-06 — Hosting defaults: `TrustForwardedHeaders` is on, a test locks it on, and Origin validation is not in the plan
- **Severity**: medium (configuration seam, not yet wired)
- **Area**: hosting / defaults
- **Where**: `Web/appsettings.json` (`Hosting:TrustForwardedHeaders: true`, `Admin:BootstrapToken: ""`), `tests/…/ScaffoldConfigurationTests.cs:39` (`Assert.True(… TrustForwardedHeaders …)`), `docs/backlog.md` (Milestone 3: «forwarded-header ordering»), handoff §14 and §"Admin".
- **What**:
  - **Forwarded headers.** The shipped default trusts `X-Forwarded-*` from any client, and a scaffold test asserts that value, so changing it to the safe default fails the build. A gateway that issues OAuth metadata, redirect URIs and audit/rate-limit keys from the request's scheme, host and remote address must trust them only from a configured proxy (`KnownProxies`/`KnownNetworks`); the backlog item names the *ordering* and says nothing about the trust list.
  - **Empty secrets.** `Admin:BootstrapToken` and the connection strings default to `""`. When the host is built, an empty token must mean "admin disabled", never "empty token accepted"; nothing records that requirement or tests it.
  - **MCP over HTTP.** The Streamable HTTP transport requires servers to validate the `Origin` header against DNS-rebinding; `grep -i origin docs` finds nothing in backlog, roadmap or handoff, and the MCP spike only sets `AllowedHosts`.
- **Suggested fix**: default `TrustForwardedHeaders` to `false` (or require a non-empty `KnownProxies` when `true`) and change the test to assert the safe default; add backlog items for the proxy trust list, the empty-token rule and Origin validation on `/mcp`; add the startup-validation tests when the host lands.
- **Confidence**: high on the configuration and the test; medium on the spec statement (from the MCP transport specification, to be re-checked against the version in ADR 0003).

### TS-07 — Activation is a timestamp race with a caller-supplied clock, and reading the active revision loads the whole history
- **Severity**: medium–low (documented as single-instance v1)
- **Area**: persistence
- **Where**: `Persistence/CatalogStore/CatalogRevisionStore.cs` (`GetActiveAsync`: `ToListAsync()` of every row with `ActivatedAt != null`, ordered in memory; `ActivateAsync(id, activatedAt)`), `StoredCatalogRevision.Activate`, `CatalogBootstrapCoordinator.RunAsync`, `docs/decisions/0014-…md`, `tests/…/CatalogRevisionStoreTests.cs` (`ActivatingTheSameRevisionTwiceOverwritesItsActivatedAtTimestamp`).
- **What**:
  - "Active" is *the row with the greatest `ActivatedAt`, then `Id`*, and `ActivatedAt` is supplied by the caller. `ActivateAsync(id, t)` with a `t` earlier than the current active revision's timestamp (clock skew between two instances, a restored clock, a test clock) **succeeds and activates nothing**: the call returns normally and the previous revision stays active. Re-activating a revision overwrites its previous `ActivatedAt` (asserted by a test), so the activation history the ADR calls "a harmless trail" is not one.
  - `GetActiveAsync` materialises **every** revision that was ever activated, *including* `TechnicalCatalogJson` and `MergedCatalogJson`, to sort them client-side because SQLite cannot order by `DateTimeOffset`. With `AlwaysImport` (one revision per start) or frequent refreshes the cost of every call is O(history × catalog size), and nothing prunes revisions. Failed revisions are persisted on every attempt, too: with an overlay that never validates and no active revision, each start appends a failed row carrying the full technical catalog.
  - The ADR accepts the ordering workaround for "a single-instance v1"; the same method will be the hot path of any "get the catalog" call unless the host caches it.
- **Suggested fix**: an `ActivationSequence` (monotonic integer) or a single-row pointer updated in the same transaction, with `ActivateAsync` returning whether it changed the active revision; project the active row's *id* first (`Select(r => new { r.Id, r.ActivatedAt })`) and load the JSON only for the winner; a retention setting for old and failed revisions; deduplicate failed revisions by `(technicalHash, overlayHash)`.
- **Confidence**: high.

### TS-08 — The "structural" hash includes `column_id`
- **Severity**: low
- **Area**: hashing
- **Where**: `Core/Catalog/TechnicalCatalogCanonicalJson.cs:250` (`writer.WriteNumber("ordinal", field.Ordinal)`), `SqlServer/SqlServerCatalogProjection.cs` (`row.ColumnId` → `Ordinal`), ADR 0006 ("hashes exclude timestamps and environment-dependent values").
- **What**: `Ordinal` is SQL Server's `column_id`, which keeps gaps after a dropped column and is compacted in a restored or freshly built database. Two databases with the same logical schema (development and production, or one before and after a restore) hash differently, and a dropped column renumbers nothing but changes the next added column's id. Under `ImportIfChanged` this produces spurious re-imports; for any future "is this the same schema as environment X" comparison it produces false differences.
- **Suggested fix**: hash the *rank* of the column among the object's columns (1…n by `column_id`), not the raw id, or drop ordinals from the hash and keep field order.
- **Confidence**: high on the mechanism; the effect is minor.

### TS-09 — Overlay `source` references split at the first dot
- **Severity**: low
- **Area**: overlay
- **Where**: `Core/Catalog/SemanticOverlayImporter.cs` (`ParsePhysicalReference`: `reference.IndexOf('.')`).
- **What**: `[my.schema].[Orders]` is addressed as `my.schema.Orders`, parsed as schema `my`, object `schema.Orders`: it never resolves and the error says only that the source "does not resolve to a discovered physical table or view". Schemas containing a dot cannot be referenced at all. Object names containing dots work by accident. Combined with the ordinal, case-sensitive matching (documented in ADR 0010), the common failure for an administrator is a "not found" with no hint about casing or the dot.
- **Suggested fix**: accept a quoted/bracketed form (`"my.schema"."Orders"`), and make the error list the nearest existing identities (case-insensitive match first).
- **Confidence**: high.

### TS-10 — CI and supply-chain hygiene
- **Severity**: low
- **Area**: CI
- **Where**: `.github/workflows/ci.yml` (`actions/checkout@v5`, `actions/setup-dotnet@v5`), no `.github/dependabot.yml`, `spikes/mcp-sdk/verify.sh`.
- **What**: the actions are referenced by movable tags; the repository is public and has no dependency-update automation; a restore-time advisory (`NU1903` on `Testcontainers.MsSql`, recorded in `development-state.md`) already broke a CI run, which shows the gate works but also that nothing proposes the fix. `CI` runs on every push to every branch with `contents: read` (good). The MCP spike's `verify.sh` requires `rg` (ripgrep) without saying so and writes its server log to a fixed `/tmp/thesqlodatamcp-mcp-sdk-server.log`.
- **Suggested fix**: pin actions by SHA with Dependabot for `github-actions` and `nuget`; make the spike scripts use `grep -q` and `mktemp`.
- **Confidence**: high.

## Checked and held (not reported)

- **No caller input reaches SQL.** The introspector's query is a constant; the connection string and timeout are the only inputs; the commented decision "no static ORM model" is honoured. `CommandBehavior.SequentialAccess` is used with strictly ascending column reads.
- **Hash discipline.** `CatalogRevisionMapper` recomputes both hashes on write and on read and refuses mismatches; `StoredCatalogRevision` enforces the succeeded/failed shape at construction.
- **Concurrency of the schema evaluator.** The static `JsonSchema` is evaluated under a lock, with the 200-iteration regression test the development state describes; the earlier bypass is fixed in the code.
- **Duplicates are rejected at construction** (`TechnicalCatalog.CopyDistinct`): two overlay entities for one source, repeated map keys, repeated relationship pairs — so the merger's last-wins dictionary assignment cannot be reached through the public constructors.
- **Type mapping.** The decimal, float, temporal and character bands I re-derived (`decimal` length bands 5/9/13/17; `time`/`datetime2`/`datetimeoffset` length and precision by scale; `money`/`smallmoney`; `datetime`/`smalldatetime`) agree with SQL Server's catalog values; unknown and user-defined type names stay `unknown`.
- **Source-database privilege** is tracked (`docs/backlog.md:111`, "verify source-database least privilege and inability to write independently of application validation") and the architecture states the identity must be read-only even if validation fails; the introspector itself does not check its login and need not until Milestone 2.
- **Secrets.** No credentials or tokens in the tree; the fixture container password is generated per run; `.gitignore` excludes local configuration and databases; the historical `changelog.md` lines about a bearer token in `settings.json` describe the removed proof of concept.
- **CI shape.** `permissions: contents: read`, a validate job before the SQL Server job, `dotnet format --verify-no-changes`, warnings as errors, an offline link check.
- **Honesty of the documents.** The README says plainly that there is no runnable gateway and that Milestone 2 has not started; the development state records its own corrections.

## Resolution

Not triaged yet. Suggested order: TS-01 and TS-02 together (they define what "exposed" means and where it is enforced, and everything downstream depends on it), then TS-03 (one coordinator change plus two tests), TS-06 (flip the default and the test), TS-04 and TS-05 (input hardening and diagnostics), then TS-07 to TS-10. Under this repository's operating model each fix should also get an independent review before acceptance, and the three highest findings should land with a backlog item and an ADR consequence so that the rule survives the next change of implementer.
