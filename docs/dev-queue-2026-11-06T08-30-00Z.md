## How to work from this list

1. Take the first open ticket whose dependencies are done. One ticket = one commit (or a small series), on `main`.
2. Each ticket states the **acceptance oracle**: the test that must exist and pass. Write that test first.
3. After each ticket: build, the full non-SQL test run, formatter, Markdown links. Record in `docs/development-state.md`
   one line: `ID | status | commit | test counts`. Statuses: TODO / DONE_PENDING_CHECKPOINT / ACCEPTED.
4. **Do not run adversarial QA yourself and do not fix the QA reports.** At each *checkpoint* below, tell the owner
   "checkpoint X is ready (SHA)"; the orchestrator audits that SHA and either accepts it or returns a short list.
5. Anything marked **OWNER** is a decision, not code: do not guess it; leave the ticket blocked and continue with the next
   ticket that does not depend on it.
6. Not in scope unless a ticket says so: new providers, UI, deployment, new protocol features, rewriting accepted slices.

## Phase A — close the input boundary (do first; independent of everything else)

These four tickets are small, independent of the SQL work, and must land before any host is written. Each probe in the
QA report is the regression oracle.

### SQL-A1 — CQM request guard before schema evaluation  *(M, no dependency)*
- **Why:** QA TS4-01/02: 636 bytes → 17 s / 3.2 GB; 4.7 MB → 5.5 GB.
- **Do:** in `Core/Cqm`, add `CqmLimits` (record with defaults taken from `Query:*` config: max bytes, max JSON depth,
  max tokens, max `select`/`joins`/`groupBy`/`orderBy`/`arguments` lengths) and a **single-pass `Utf8JsonReader` scan**
  that runs first in `CqmJson.Deserialize` and returns `CqmValidationErrorCodes.LimitExceeded` with a stable `$.path`.
  Take the `byte[]/ReadOnlySpan<byte>` overload as the primary entry (avoid parsing the same text three times).
  Add `maxItems`/`maxLength` to `cqm.v1.schema.json` as documentation of the same limits.
- **Accept:** (a) depth-14 nested `not` (636 B) is rejected in < 50 ms with < 10 MB allocated; (b) 100,000-item `select`
  (4.7 MB) is rejected in < 200 ms before any `JsonNode`/schema work; (c) a document exactly at each limit still parses;
  (d) the existing 359 tests unchanged. Use `GC.GetAllocatedBytesForCurrentThread()` and a `Stopwatch` bound in the tests.

### SQL-A2 — CQM expression validation linear in depth  *(M, after A1)*
- **Why:** the exponential cost is in `oneOf` over every expression shape at every level (`cqm.v1.schema.json:196`).
- **Do:** make expression typing the job of the typed converter/validator (it already knows the six shapes) and keep the
  published schema as contract/documentation, **or** restructure the schema so each level has a single deterministic
  branch (`if`/`then` keyed on the discriminating property). Choose by measurement; do not change accepted/rejected
  documents.
- **Accept:** a valid expression nested to the configured maximum depth (20) parses in < 100 ms and < 50 MB; the whole
  existing `CqmJsonTests` corpus gives identical accept/reject results and the same error paths.

### SQL-A3 — evaluation concurrency  *(S, after A2)*
- **Why:** `CqmSchema.EvaluationLock` serialises every parse; its comment ("validation is cheap") was false before A2.
- **Do:** after A2, measure 8 parallel parses of a mid-size document vs sequential; if parallel is not ≥ 3× faster,
  remove the shared evaluator from the hot path. Keep the importer's lock (rare, administrative).
- **Accept:** a test that parses 8 documents in parallel and asserts results are identical to sequential, and records the
  elapsed-time ratio in the test output.

### SQL-A4 — overlay parsing cannot crash or throw  *(M, no dependency)*
- **Why:** QA TS4-03/04: 400 KB of `[` stack-overflows YamlDotNet; deep Markdown throws `ArgumentException`; the Markdown
  cap is not applied to the combined front-matter path.
- **Do:** (1) bound nesting **before** building the tree — replace `YamlStream.Load` with YamlDotNet's event `Parser`
  and an explicit depth/node counter that builds the `JsonNode` iteratively, or pre-scan flow-collection depth; (2) apply
  `MaxYamlCharacters`/`MaxMarkdownCharacters` to the **whole** front-matter document before `Markdown.Parse`;
  (3) catch `Exception` (excluding fatal ones) around parse/convert and return `overlay.yamlSyntaxInvalid` /
  a new `overlay.markdownInvalid`.
- **Accept:** inputs of depth 200,000 and 1,000,000-character `[`, 1.9 M `>`, 1.9 M `[` and a 3.9 MB nested list all return
  a structured `Failure` (never an exception, never a crash); an alias bomb and duplicate keys keep their current results.
  The crash cases must run in **a child process** (see A5) because a stack overflow kills the test host.

### SQL-A5 — child-process harness for resource tests  *(S, with A4)*
- **Do:** a small xUnit helper `ProcessIsolated.Run(name, args, maxSeconds, maxMemoryMb)` that launches the test host
  (or a tiny `Probe` project in `tests/`) with `DOTNET_GCHeapHardLimit`, a timeout, and asserts the exit code and the last
  output line. Used by A1 (memory), A4 (stack depth).
- **Accept:** the harness fails the build if a probe exits with a fatal signal or exceeds its limits.

> **CHECKPOINT A** — all of A1–A5 in `main`, CI green on that SHA. Orchestrator reruns the QA probes and accepts or returns
> a list. Nothing in Phase B waits for it, but **no host code (SQL-07 onward) starts before it is accepted**.

## Phase B — the plan's first steps, in ticket-size pieces

### SQL-00 — OWNER decisions (blocking only the tickets that name them)
Answer in `docs/decisions/` as one short ADR ("v1 support matrix"). Recommended defaults in italics:
1. SQL Server versions supported for the *source* database: *2019, 2022, 2025; CI exercises 2022.*
2. Operating systems/artifacts: *Windows x64 and Linux x64 self-contained + Docker image (handoff §29).*
3. MCP clients that must be proven end to end: *MCP Inspector plus one real desktop client chosen by the owner.*
4. Default exposure: *keep "visible unless excluded" **but** require a non-empty `DataSource:IncludedSchemas` at startup
   (no implicit `dbo`)* — this is the safe reading of the handoff and what SQL-01a assumes.
5. Public guide: *an administrator-written `publicGuide` field in the overlay is what `get_reporting_guide` returns; the
   catalog narrative stays internal* (TS3-02 removed it from the public view).

### SQL-01a — `IncludedSchemas` / `ExcludedObjects` in the introspector  *(M; needs decision 4)*
- **Do:** pass `DataSourceOptions` to `SqlServerCatalogIntrospector`; apply both lists **in the SQL** (parameterised,
  fixed text otherwise); define what happens to foreign keys whose target is outside the boundary (*drop the relationship,
  record a warning in the revision*, do not throw "FK target is not part of the technical catalog"); validate the options
  at startup.
- **Accept:** on the reporting fixture extended with a second schema and a cross-schema FK: excluded objects are absent
  from the technical catalog JSON, the control store and every log; the cross-schema FK yields a warning, not an exception;
  an empty `IncludedSchemas` fails validation with the key name.

### SQL-01b — introspection diagnostics and unusual metadata (TS-05)  *(M)*
- **Do:** every projection/type-mapper failure carries `schema.object[.column]`; unknown structural metadata
  (ledger `generated_always_type` 5–8, graph, in-memory, external tables) is *skipped with a named warning* instead of
  failing the whole catalog; keep strict failures for genuinely inconsistent metadata, but named.
- **Accept:** fixture/unit cases for a ledger column, a graph table and a corrupt decimal metadata row: first two → catalog
  built + warnings; the third → one error naming the column. (Add the ledger table to the SQL fixture only if the fixture
  image supports it; otherwise unit-level on `SqlServerCatalogProjection`.)

### SQL-01c — one public catalog boundary  *(S)*
- **Do:** expose only `CatalogReadView` to `Protocols`/`Web` (internal constructors elsewhere, or an `ICatalogSnapshot`
  interface returning the read view); extend `CoreBoundaryTests`/`ProtocolBoundaryTests` with a reflection rule: no
  public type outside `Core` exposes `MergedCatalog`/`TechnicalCatalog`.
- **Accept:** the boundary test fails if such a member is added.

### SQL-01d — public guide path  *(S; needs decision 5)*
- **Do:** add the overlay field and a `CatalogReadView.PublicGuide`; schema + importer + canonical JSON + hash.
- **Accept:** round-trip, hash changes with the field, absent field → `null`, hidden-object names in the guide are the
  administrator's responsibility (documented, not "redacted").

> **CHECKPOINT B** — SQL-01a–d. Orchestrator reruns the discovery/exposure probes on the real SQL fixture (remote CI) and
> checks that no hidden object name appears in any serializer.

### SQL-02 — resolve CQM identifiers against one immutable revision  *(L → split)*
- **02a** `ICatalogSnapshot` (immutable `CatalogReadView` + revision id) and `CqmBinder` for `from`, joins' sources, field
  references and aliases: unknown/hidden/ambiguous names fail with stable paths. *(M)*
- **02b** projection output columns, duplicate/ambiguous alias rules, `orderBy`/`having` alias resolution. *(M)*
- **02c** "one query, one revision": the binder captures the snapshot once; a test activates a new revision between bind
  and use and proves the old snapshot is still the one used. *(S)*
- **02d** `page.limit`/`offset` and query limits are validated here against `Query:*` (the schema accepts up to
  2,147,483,647). Unwired `Query:*` keys become a validated options type. *(S)*
- **Accept:** table-driven tests for hidden (`exposed:false`), unknown, case-different and duplicate names; no source
  identifier is ever built from request text.

> **CHECKPOINT C** — Phase A + SQL-01 + SQL-02. Only then the plan's SQL-03 (types) … SQL-06 (execution) proceed.
