## Attacks on the new code

1. **The runtime schema no longer evaluates `expression`; `CqmExpressionShapeValidator` is a hand-written copy of the
   six-form contract.** This is the classic place for a silent divergence (a document the published schema rejects but
   the runtime accepts). Differential test: 60,000 random expression trees (3 seeds × 20,000; depth ≤ 3, with
   mutations: extra properties, mixed forms, empty `arguments`, unknown operators/functions/aggregates, bad `field`
   and `alias` patterns, `type`/`value` mismatches, non-object expressions), evaluated by the **published** schema
   (a fresh `JsonSchema` from `CqmSchema.Json`) and by `CqmJson.Deserialize`. About 17,500 of them are valid by the
   published schema. Result: **no document accepted by the runtime that the published schema rejects**, and no
   document rejected with a shape/limit code that the published schema accepts, except one literal (see TS5-03). The
   remaining runtime-only failures are the semantic codes that always came after the schema stage
   (`unknownAlias`, `operatorArityInvalid`, `aggregateNotAllowedHere`, `deserializationFailed`).
2. **The request guard** (`CqmRequestGuard`) matches arrays by *property name* (`select`, `joins`, `groupBy`,
   `orderBy`, `arguments`). Probed: `groupBy`/`orderBy`/`joins` ×100,000 rejected in ≤ 1 ms; `page.limit` over the
   maximum rejected at the boundary; a literal `value` array of 190,000 numbers (371 KB) is *not* limited by name but
   costs 383 ms / 210 MB, bounded by `MaxBytes`/`MaxTokens`; nested arrays in a literal are bounded by
   `MaxJsonDepth` (depth 60 accepted in 1 ms). Malformed JSON still produces the established `cqm.jsonInvalid`.
3. **Worst in-limit valid document**: `and` of 100 `or` of 100 `eq` (607 KB, ~10,000 nodes) parses in 721 ms / 151 MB.
   Acceptable for the stated limits.
4. **YAML guard** (`GuardYamlShape`): iterative event pull before `YamlStream.Load`. The node cap (`MaxYamlNodes`
   100,000) holds: 120k scalars rejected in 188 ms; 90k scalars (just under the cap) cost 2.9 s / 431 MB once, 80k
   scalars 1.8 s — linear, bounded, and slow only because the later schema evaluation runs over that many nodes.

## Findings

### TS5-01 — low — validation error lists are not capped
- **What:** an invalid document produces one error per offending node, with no ceiling. A 156 KB overlay whose
  `entities` is a flow sequence of 80,000 scalars returns **80,001 errors / 6.6 MB of error text (42× the input)**.
  A 195 KB CQM with 1,000 bad `select` fields and 10,000 bad leaves returns 11,000 errors / 1.4 MB (7×).
- **Why it matters:** the input is bounded now, the output is not proportional to it. When a host exists, the error
  list becomes a response body and a log entry; the amplification turns a 150 KB request into a multi-megabyte answer
  (and, in a server, into allocation per request).
- **Fix direction:** keep the first N errors (e.g. 100) in both result types and add a marker such as
  `truncated: true` plus the total count; test with the probe inputs above (queue SQL-A6).
- **Confidence:** high (measured, `errs` probe). **Not reachable today** — there is no host — hence low.

### TS5-02 — low — the `Query:*` configuration is still not read (TS4-06 carried)
- `CqmLimits` now carries the same numbers as `appsettings.json` (`MaxPageSize` 5000, `MaxJoins` 8,
  `MaxGroupByFields` 12, `MaxExpressionDepth` 20) as **constants** in `CqmLimits`; nothing binds the `Query` section.
  Changing the file changes nothing. This is a gap only once a host exists: at that point bind the section into
  `CqmLimits` in one place and test that a value in the file changes the verdict (queue SQL-A6, together with TS5-01).

### TS5-03 — info — an external evaluator of the published schema can accept an out-of-range `int64`
- `{"value":99999999999999999999,"type":"int64"}` is **valid** under the published schema as evaluated by JsonSchema.Net
  (12 of 60,000 cases) and is **rejected** by `CqmJson.Deserialize` (`cqm.schemaViolation $.where.value`). The runtime
  is right; the observation is for the public guide (SQL-01d): a client that validates against the published schema
  alone can accept what the server refuses. Say so in the guide and, if cheap, tighten the schema (`maximum` on a
  number the evaluator compares as `decimal`).
