## New CQM findings

### TS2-01 — medium — automatic joins required by the baseline are unrepresentable

- **Where:** `src/TheSqlODataMcp.Core/Cqm/CqmQuery.cs:125-147`,
  `src/TheSqlODataMcp.Core/Cqm/Schemas/cqm.v1.schema.json:106-145`, `docs/decisions/0016-cqm-v1-contract.md:16`;
  authoritative handoff §7.
- The handoff requires explicit `on`, else named `relationship`, else one unambiguous discovered/configured relationship.
  Constructor and schema require **exactly one** of `on` / `relationship`, so the third representation cannot exist:

```json
{"version":"1.0","from":{"entity":"sales.Secrets","alias":"s"},
 "page":{"limit":10,"offset":0},
 "joins":[{"type":"inner","source":{"entity":"sales.Other","alias":"o"}}]}
```

Actual result: `success=False; cqm.schemaViolation@$.joins[0]`. Direct construction also throws. The join resolver
is intentionally deferred, but its DTO must be able to carry a request for automatic resolution before it exists.
The lower-priority Proposed ADR cannot silently remove that settled product requirement.

- **Action applicata:** `CqmJoin` now allows **at most one** of `on`/`relationship`; both absent means automatic
  resolution, and both present remains invalid. The published schema uses a `not` constraint instead of requiring one.
  Direct-construction and JSON regression tests cover the automatic state and reject the both-present state. The
  resolver itself stays in the later join-resolution slice, as required.
- **Status: risolto localmente** per il contratto; la semantica automatic/ambiguous/explicit-override resta da
  implementare e testare nel resolver, non è dichiarata eseguibile.

### TS2-02 — medium — temporal literal validation accepts incomplete and host-dependent values

- **Where:** `src/TheSqlODataMcp.Core/Cqm/CqmExpression.cs:88-95`; `docs/cqm.md:46-53`.
- The predicates use permissive `TimeOnly.TryParse` / `DateTime.TryParse` / `DateTimeOffset.TryParse`, not a defined
  wire grammar. In the same otherwise valid query, these literals were all **accepted**:

```text
type=time           value="November 2"           success=True
type=time           value="2026-11-02T12:30:00"   success=True
type=datetime       value="12:30"                success=True
type=datetimeOffset value="12:30"                success=True
type=datetimeOffset value="2026-11-02T12:30:00"   success=True
```

The parser preserves the original string; no database execution happened. Nevertheless a time literal can be a date,
and a datetime/offset literal can omit its date/offset. Subsequent conversion can invent the current day/year or
machine timezone, contradicting a deterministic, typed public contract. Overprecision such as nine fractional digits
also passes datetime parsing without a documented precision policy.

- **Action applicata:** the canonical grammar is now explicit and culture/timezone independent:
  `time` = `HH:mm:ss` or `HH:mm:ss.FFFFFFF`; `datetime` = complete `yyyy-MM-ddTHH:mm:ss` with optional 1–7 fractional
  digits and **no** offset; `datetimeOffset` = the same complete date/time plus mandatory `Z` or `±HH:mm`, with optional
  1–7 fractional digits. `date` remains `yyyy-MM-dd`. Incomplete values, date-only datetimes, missing offsets and
  nine-digit fractions are rejected by exact parsing. Tests cover all three types and the QA literals.
- **Status: risolto localmente.** No normalization/rounding is applied; values outside the grammar are rejected.

## Catalog follow-up: previous findings now exercised

### TS-04 supplemental — medium — ordinary invalid YAML escapes the collected-errors contract

- **Where:** `src/TheSqlODataMcp.Core/Catalog/SemanticOverlayImporter.cs:88-106,126-136,165-170,465-467`.
- Independent probes against a valid one-entity `TechnicalCatalog`:

```yaml
catalogVersion: '1.0'
entities: [null]
```

Actual: **`NullReferenceException`** at reference validation. Schema errors are collected, but traversal of the invalid
typed DTO continues without checking the null entity. This is a normal malformed input, not a resource-exhaustion test.

```yaml
catalogVersion: '1.0'
entities: []
name: 1e400
```

Actual: **`OverflowException: Value was either too large or too small for a Decimal.`** Conversion produces a non-finite
double, and the schema-evaluation call is outside a handling boundary. A duplicate mapping key was also tested and
correctly returned `overlay.yamlSyntaxInvalid`: the old report's speculation that duplicate keys might escape is
**not confirmed** and must not be repeated as a demonstrated defect.

- **Action applicata:** null entity/field subgraphs now produce stable `overlay.schemaViolation` errors instead of
  `NullReferenceException`; non-finite numeric scalars produce `overlay.numericOutOfRange`; schema-evaluator decimal
  overflow is caught and reported; YAML is bounded to 1,000,000 characters, 64 levels and 100,000 nodes, and Markdown
  to 2,000,000 characters. The four QA probes are permanent regression tests.
- **Status: risolto localmente.** Duplicate YAML keys still correctly return `overlay.yamlSyntaxInvalid`.

### TS-03 — high-priority before hosting — overlay-only refresh still silently returns the old revision

- **Where:** `src/TheSqlODataMcp.Persistence/CatalogStore/CatalogBootstrapCoordinator.cs:38-44`.
- Real file-backed SQLite, real migrations: first bootstrap with `ImportIfChanged`, same physical catalog with default
  exposure; then bootstrap the same catalog with an overlay setting that entity to `exposed:false`.
- Actual: **`first=1, second=1, still exposed=True`**, no failed revision or rejection. The changed overlay is not
  considered because only the technical hash is compared. This is a reproduced defect in the present library, not an
  allegation of an already-public leak.
- **Action applicata:** `CatalogBootstrapCoordinator` builds a candidate revision and compares status, technical hash,
  merged hash and serialized validation outcome. An overlay-only `exposed:false` change now creates and activates a new
  revision; an unchanged overlay stays skipped; a failed candidate does not activate. Real-SQLite regression added.
- **Status: risolto localmente.**

### TS-01 — exposure seam confirmed, not an existing network vulnerability

- **Where:** `src/TheSqlODataMcp.Core/Catalog/CatalogSearchIndex.cs` and `MergedCatalog` / `MergedEntity`.
- A merged entity with `Exposed=False` produced **`search count=1, lookup found=True`** in the existing internal index.
  Merge intentionally retains all metadata; no protocol endpoint exists. The defect would be wiring an unfiltered
  index directly to external catalog APIs. That missing public-view gate must be explicit in the backlog and tested.
- **Action applicata:** `CatalogReadView` is the exposed-only core boundary: it filters hidden entities, removes
  relationships whose target is hidden/absent, and omits catalog-level warnings/Markdown that may mention hidden
  objects. `FindEntity`/`Search` operate on the filtered view. Tests prove hidden lookup/search denial and hidden-target
  relationship removal, while the internal index keeps the administrative metadata.
- **Status: risolto nel Core; il wiring degli adapter a `CatalogReadView` resta un gate esplicito di Milestone 3/4.**
  Non esiste ancora un endpoint pubblico, quindi non è una vulnerabilità di rete corrente.

### TS-07 supplemental — medium — bootstrap's returned revision and persisted active revision can disagree

- **Where:** `src/TheSqlODataMcp.Persistence/CatalogStore/CatalogRevisionStore.cs:43-54,65-71`,
  `CatalogBootstrapCoordinator.cs:55-56`.
- Real SQLite: create/activate revision 1 at `t`; run `AlwaysImport` for revision 2 at `t - 1 minute` (clock rollback).
  Actual: **`coordinator returned=2; actual active=1; disagreement=True`**. The coordinator promises the returned row
  should now be treated as active, whereas the store chooses greatest `ActivatedAt`. No concurrent process is needed.
- **Action applicata:** activation timestamps must strictly increase; an earlier clock or an equal timestamp with an
  older/equal id is rejected before touching the active row. `GetActiveAsync` projects only id/timestamp for selection
  and loads the full JSON blob once for the winner. A real-SQLite regression reproduces the rollback and proves the
  previous revision stays active.
- **Status: risolto localmente.** The coordinator still throws on the rejected activation instead of returning the old
  row, so no caller can receive a revision that `GetActiveAsync` would not select.
