## Verdict

**The foundation is correct, and the documentation of it is honest. Two resource-exhaustion defects in the
input boundary are not covered by any test or plan step and must be fixed before any host exists.**

- Independently reproduced: build 0 warnings / 0 errors, **357 / 357 non-SQL tests pass** (the dev's count), and the
  fixes of TS-01/03/04/07 behave as documented.
- **New, high:** a **636-byte** CQM document (14 nested `not` operators) needs **17 s and 3.2 GB** to be parsed; four more
  levels do not finish on a 16 GB machine. A 4.7 MB document with 100,000 select items needs **5.5 GB**. The published
  limits (`Query.MaxExpressionDepth: 20`, `MaxPageSize`, …) are configuration text that nothing reads.
- **New, high:** a 400 KB YAML overlay made of nested `[` **terminates the process** with a stack overflow inside
  YamlDotNet's parser, below the importer's own 1,000,000-character cap. The importer's depth limit (64) runs *after*
  the library has already recursed.
- None is reachable today (no host), which is exactly why they are cheap now: the SQL-06/07/08 steps would otherwise
  build the HTTP surface on top of a parser that dies on a 700-byte request.

## Findings

### TS4-01 — high — CQM schema evaluation is exponential in expression nesting
- **Where:** `src/TheSqlODataMcp.Core/Cqm/CqmJson.cs` (`CqmSchema.Compiled.Evaluate`), `Cqm/Schemas/cqm.v1.schema.json:196`
  (the recursive expression definition is a `oneOf`), `Cqm/CqmSchema.cs`.
- **Probe (Release, `CqmJson.Deserialize`):** `{"version":"1.0","from":…,"page":…,"select":[…],"where": NOT(NOT(…NOT(true)))}`

  | nested `not` depth | document | time | process RSS |
  | --- | --- | --- | --- |
  | 8 | 438 B | 176 ms | 117 MB |
  | 10 | 504 B | 1.4 s | 319 MB |
  | 12 | 570 B | 3.9 s | 852 MB |
  | 14 | 636 B | **17.4 s** | **3.2 GB** |
  | 16 | 700 B | not finished after > 60 s; the machine was at ~12 GB used; killed | — |

  Each two extra levels multiply time and memory by roughly 3 to 4.5: the cost is the combination of a `oneOf` over every
  expression shape at every level. `System.Text.Json`'s default depth limit (64) is the only bound and it allows ~20
  expression levels; the typed validator that would enforce `MaxExpressionDepth` runs **after** the schema, i.e. too late.
- **Why it matters:** a 700-byte unauthenticated-looking request is a process-wide out-of-memory. The CQM parser is the
  first thing every adapter (JSON, MCP, OData translation) calls.
- **Fix direction (ticket SQL-A1/A2 in the queue):** a single-pass `Utf8JsonReader` guard *before* schema evaluation
  (bytes, depth, token count, array lengths), plus a schema or evaluation strategy that is linear in depth.
- **Confidence:** high (measured). The exact numbers depend on the machine; the growth rate does not.

### TS4-02 — high — memory amplification by width (no `maxItems`, no body bound)
- **Where:** `cqm.v1.schema.json` has **no `maxItems`** anywhere and `page.limit` allows up to 2,147,483,647;
  `appsettings.json` `Query.*` is only referenced by the scaffold test (`grep MaxExpressionDepth|MaxJoins|MaxPageSize|MaxRows src` → none).
- **Probe:** `select` with N items of `{"expression":{"field":"i.Id"},"alias":"aN"}`: 1,000 items (45 KB) 0.19 s / 127 MB;
  10,000 items (467 KB) **4.2 s / 709 MB**; 100,000 items (4.7 MB) **34 s / 5.5 GB**. About 1,100 bytes of memory per byte of input.
- **Why it matters:** the budgets promised in the plan (SQL-06) arrive after the parse; even a correct request-size cap
  at the host would have to be set from this measurement, not from the 10 MB result limit.
- **Confidence:** high.

### TS4-03 — high — deeply nested YAML kills the process before the importer's guards run
- **Where:** `SemanticOverlayImporter.cs` — `ParseYamlToJson` calls `YamlStream.Load` (recursive `YamlNode.ParseNode`);
  the limits `MaxYamlCharacters = 1,000,000`, `MaxYamlDepth = 64`, `MaxYamlNodes = 100,000` are applied in
  `ConvertYamlNode`, i.e. on the already built tree.
- **Probe:** `catalogVersion: "1.0"\nentities: [[[[ … ]]]]` — depth 1,000 → structured `overlay.yamlSyntaxInvalid` (36 ms);
  depth 20,000 → structured error (1.5 s); **depth 200,000 (≈ 400 KB, under the character cap) → `Stack overflow` in
  `YamlDotNet.RepresentationModel.YamlNode.ParseNode`, process terminated.**
- **Also verified fixed:** an alias bomb (9 levels × 9 references) → rejected in 42 ms by the node cap; duplicate mapping
  keys → `overlay.yamlSyntaxInvalid`, no exception. So the earlier TS-04 fixes are real for those inputs.
- **Why it matters:** `StackOverflow` is not catchable. Any host path that imports an overlay (bootstrap file today;
  the SQL-11 upload tomorrow) can be crashed by a small file; in a unit-test host it would kill the test run.
- **Confidence:** high (reproduced; the overflow stack is in the library).

### TS4-04 — medium — `ImportMarkdownWithFrontMatter` throws for deeply nested Markdown and bypasses the Markdown cap
- **Probe:** front matter followed by 1.9 M `>` characters, 1.9 M `[`, or a 3.9 MB nested list →
  `ArgumentException: Markdown elements in the input are too deeply nested` escapes the method (the contract is a
  `SemanticOverlayImportResult.Failure`). The 3.9 MB body was handed to Markdig although `MaxMarkdownCharacters = 2,000,000`:
  the size guard is not applied on the combined front-matter path (already named in plan SQL-01, "bound combined front
  matter before Markdown parsing"). 1.9 M `*` characters parse normally.
- **Confidence:** high.

### TS4-05 — medium — one global lock serialises every CQM parse, and its justification is wrong
- **Where:** `CqmSchema.EvaluationLock` (`CqmSchema.cs`): "Validation is cheap relative to actual query execution."
  TS4-01/02 show evaluation is neither cheap nor bounded, so one hostile or large document stalls **every concurrent
  request** behind the lock (the importer has the same pattern, acceptable there because imports are rare).
- **Fix direction:** make evaluation cheap first (TS4-01); then either remove the shared mutable evaluator from the hot
  path (typed validation only, schema as published contract/documentation) or measure that parallel parses do not
  degrade. Do not remove the lock before the concurrency defect that motivated it is understood.
- **Confidence:** high on the code; the contention effect follows from TS4-01 (not separately timed).

### TS4-06 — low — configuration limits exist only as text
- `Query.MaxPageSize = 5000`, `MaxRows`, `MaxJoins`, `MaxGroupByFields`, `MaxAggregates`, `MaxExpressionDepth`,
  `MaxConcurrentQueries`, `MaxResultBytes` appear in `appsettings.json` and `ScaffoldConfigurationTests`, and nowhere
  else. They are declared here only so nobody reads them as implemented controls; the owner steps are SQL-06/07.
